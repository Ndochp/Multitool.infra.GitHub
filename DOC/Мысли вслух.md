# Начало 
(Оно же промт для копилота)
Необходимо разработать архитекутуру по изоляции репозитория программного продукта (1С конфигурации) и инфраструктурной CI обвязки.
Это необходимо, так как 
1.  при пуликации git репозитория с приложением мы не должны зависеть от того, какие средства CI будут у тех, кто форкнет его. Репо с приложением должно содержать только то, что относится непосредственно к приложению - архитектурное описание, код приложения, тесты. 
2. Репозиторий с CI автоматизацией имеет собственный цикл разработки и может быть переиспользован для различных репозиториев 1С конфигураций.

Сценарий использования предполагается следующий: разработчик форкает репозиторий приложения, репозиторий подходящей для его CI инфраструктуры, настраивает переменные окружения на своем Git/CI сервере и получает возможность прогонять необходимые тесты для CI/MR в репозиторий приложения, формировать и публиковать релизные артефакты после обновления мастер ветки.


Для повышения конкретики - пока предполагаеся что репозиторий приложения будет опубликован на гитхаб (Ndochp/multitool), в этом репозиториии - описание архитектуры такого разделения и инфраструктурная часть для CI на GitHubAction с локальным расположением исполнителя.


Ответ копилота:

Архитектура изоляции репозитория приложения и CI-инфраструктуры

1. Цели и принципы





Репо приложения содержит только: описание архитектуры, код 1С конфигурации, тесты. Без привязки к конкретному CI (GitHub Actions, GitLab CI, Jenkins и т.д.).



Репо CI-инфраструктуры — отдельный жизненный цикл, переиспользуемость для разных репозиториев 1С.



Сценарий: разработчик форкает оба репо, настраивает переменные окружения и получает тесты на CI/MR и сборку релизных артефактов.

3. Контракт между репозиториями

Репо приложения должно предоставлять:







Элемент



Описание





Структура проекта



Стандартная структура EDT (.project, src/) или структура выгрузки 1С (XML)





Команды/скрипты



Опционально: скрипты test, build в корне или scripts/, вызываемые из CI. Либо документация команд (EDT CLI, Designer batch mode)





Переменные окружения



Список необходимых: путь к 1C/EDT, учётные данные, путь к тестовой БД

Рекомендуемый документ в репо приложения: CONTRIBUTING.md или docs/CI-contract.md с описанием этого интерфейса (CI-агностично).

4. Архитектура репо Multitool.infra.GitHub

4.1 Структура





[.github/workflows/](.github/workflows/) — workflows GitHub Actions



[scripts/](scripts/) — настройка self-hosted runner (run-local-runner.sh, run-local-runner.ps1)



[DOC/](DOC/) — описание архитектуры разделения (этот план)



actions-runner — в .gitignore, создаётся скриптами

4.2 Триггеры workflow







Триггер



Описание





workflow_dispatch



Ручной запуск с параметром repository (owner/repo)





repository_dispatch



Автозапуск при событиях в репо приложения (требует минимальный workflow в app repo)





schedule



Периодическая проверка (cron) для polling-сценария

Важно: для полной изоляции app repo от GitHub Actions достаточно workflow_dispatch и schedule. Для автоматического CI на push/PR в app repo нужен либо тонкий триггер в app repo, либо внешний сервис.

4.3 Конфигурация через переменные





APP_REPOSITORY — целевой репо (по умолчанию ndochp/multitool)



GITHUB_PAT — Personal Access Token для checkout приватного репо



ONE_C_PATH — путь к 1C:Enterprise или EDT



TEST_DATABASE_PATH — путь к тестовой БД (если используется file-based IB)

4.4 Адаптация под 1С

Текущий build-pipeline.yml рассчитан на Node.js. Для 1С:





Сборка: EDT CLI (edt build) или Designer batch (1cv8 DESIGNER /DumpCfg, /LoadCfg и т.п.)



Тесты: xUnitFor1C (xddTestRunner.epf) или EDT test runner



Артефакты: выгрузка в XML/DT, публикация Release через actions/create-release, actions/upload-release-asset

Workflow должен вызывать скрипты/команды по контракту репо приложения или использовать параметризованные шаги.

5. Сценарий настройки для разработчика





Fork Ndochp/multitool (app) и fork Multitool.infra.GitHub (infra)



В infra repo: Settings → Secrets and variables → Actions: задать GITHUB_PAT, ONE_C_PATH и т.д.



В workflow infra repo задать APP_REPOSITORY: your-org/your-multitool-fork



Установить self-hosted runner для infra repo (через scripts/run-local-runner.ps1 или .sh)



Запускать workflow вручную или по расписанию; при необходимости — добавить триггер из app repo
